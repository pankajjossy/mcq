# MCQ Test Hall

Teacher/student testing app. Teachers build papers on a dedicated builder page -
mixing multiple-choice, true/false, fill-in-the-blank and match-the-following
questions, each with its own marks, generated by Gemini from pasted text or a
document - review, save, and later "upload" during class. Separately, teachers
can set short-answer papers that students answer on paper, photograph, and
submit for Gemini to grade automatically. Students see an "exam hall" landing
page listing live papers (visible for 40 minutes after upload), pick one,
answer it once, and get graded instantly. Each teacher also has a class wall
where students can post/discuss after a test, FB-style.

Everything used here is open source or has a genuinely free tier with **no credit
card required, anywhere in the stack.**

## How it works

- **Teachers** register with name + login name + password. **Students** register
  with name + semester + roll number + password.
- On the **Build a paper** page: teacher enters subject + semester, picks a
  difficulty (easy/medium/hard) and mixes question types (e.g. 2 multiple
  choice + 2 fill-in-the-blank + 1 true/false) with a count for each, then
  pastes text or uploads a `.txt`/`.docx`/`.pdf` (extracted to plain text
  right in the browser). Gemini drafts the questions; the teacher reviews,
  edits, and can raise/lower marks per question (default 1) - the total is
  whatever those add up to when they press **Done**.
- Saved papers sit collapsed in the teacher's dashboard (Upload / View / Edit /
  Delete, one confirm on delete). At class time, teacher clicks **Upload** -
  it appears on every student's landing page, labelled e.g. "Sem3 Physics 31
  Aug 26 12:45," newest first.
- The paper stays in the student's "exam hall" for **40 minutes** after
  upload, then drops off that list into the collapsed dashboard archive
  (whether or not a given student took it).
- Student clicks a paper, answers, clicks **Done** -> graded instantly
  server-side (no AI call needed for MCQ-family grading - it's a direct
  comparison against the stored answer key). One attempt per student per
  paper. After submitting, the student can post about it straight to their
  teacher's wall.
- Short-answer papers follow the same build/upload flow but with free-text
  questions and per-question marks; students photograph their handwritten
  answer to each question, and Gemini OCRs + grades on submit (the photo
  itself is never stored).
- Teacher clicks **Show Results** -> a live, auto-refreshing scoreboard - good
  for a projector.
- Both dashboards have **Subject-wise performance** and **Overall performance**
  tabs, and every past paper is a collapsed row that expands to show the
  answer key (and, on the student side, that student's own picks).
- Every teacher has a **Class Wall** (linked from their dashboard, and from
  each student's dashboard once they've taken that teacher's paper) - posts,
  replies, editable by their author, and a post can reference a specific
  paper, expandable inline to view it.

## Stack (all free, no credit card anywhere)

| Piece | Choice |
|---|---|
| Frontend | React + Vite, hosted on GitHub Pages |
| Backend | **Supabase Edge Functions** (Deno, serverless) - no separate server to host |
| Database | PostgreSQL, via the same Supabase project |
| Question generation & short-answer grading | Google Gemini API (free tier key from aistudio.google.com/apikey) |
| Document text extraction | Client-side in the browser (pdfjs-dist, mammoth) - never touches the backend |

**Why not Render/Railway/Koyeb for the backend?** As of 2026, every one of
them requires card verification before you can deploy - even to their free
tier (it's an anti-fraud measure, not a real charge, but it's still a card).
Supabase's Edge Functions need no such verification, and since there's no
separate server process to run, there's nothing that can "sleep" and cause
a slow cold start either - the two problems that plagued the earlier
Render-based version of this project (see `backend-old-express-render/` for
that abandoned attempt, kept only for reference).

## 1. Set up the database and functions (Supabase)

1. Create a free account at supabase.com (GitHub sign-in works), create a
   new project. No card needed at any point.
2. Open the **SQL Editor** and run these three files in order, pasting each
   one's contents in and running it before moving to the next:
   `supabase/migrations/schema.sql`, then `0002_short_answer_and_wall.sql`,
   then `0003_semester_and_question_types.sql`.
3. Install the Supabase CLI if you haven't already:
   ```bash
   npm install -g supabase
   ```
4. Log in and link this repo to your project:
   ```bash
   supabase login
   supabase link --project-ref your-project-ref
   ```
   (Your project ref is in the URL of your Supabase dashboard, or under
   Project Settings -> General.)
5. Set your secrets (these replace the old backend/.env):
   ```bash
   supabase secrets set DATABASE_URL="postgresql://postgres:...@...supabase.com:5432/postgres"
   supabase secrets set JWT_SECRET="any-long-random-string"
   supabase secrets set GEMINI_API_KEY="your-gemini-key"
   supabase secrets set FRONTEND_ORIGIN="https://yourname.github.io"
   ```
   Use the **Session pooler** connection string for DATABASE_URL (Project
   Settings -> Database -> Connection string) - it handles many short-lived
   connections better, which matters when a whole class submits within the
   same few seconds.
6. Deploy the four functions:
   ```bash
   supabase functions deploy auth
   supabase functions deploy teacher
   supabase functions deploy student
   supabase functions deploy wall
   ```
7. Your functions are now live at:
   `https://your-project-ref.supabase.co/functions/v1/auth` (and /teacher, /student, /wall)

## 2. Get a Gemini API key

Go to aistudio.google.com/apikey, sign in, and create a free API key. No
card required for the free tier. (As of mid-2026, new keys look like
`AQ.Ab...` rather than the older `AIza...` format - both are valid.)

## 3. Run the frontend locally

```bash
cd frontend
cp .env.example .env
# fill in VITE_SUPABASE_FUNCTIONS_URL and VITE_SUPABASE_ANON_KEY
# (both from Supabase: Project Settings -> API)
npm install
npm run dev
```

It starts on http://localhost:5173 and talks directly to your deployed
Edge Functions - there's no local backend process to run alongside it.

## 4. Deploy the frontend (GitHub Pages, free - fully automatic)

1. In your GitHub repo: Settings -> Secrets and variables -> Actions, add
   two repository secrets: `SUPABASE_FUNCTIONS_URL` (e.g.
   `https://your-project-ref.supabase.co/functions/v1`) and
   `SUPABASE_ANON_KEY` (from the same Supabase API settings page).
2. Settings -> Pages -> Source, choose GitHub Actions.
3. Push to main - `.github/workflows/deploy-frontend.yml` builds
   `frontend/` with Vite and publishes it automatically. Check the Actions
   tab for progress; the deployed URL appears there and under
   Settings -> Pages once done.
4. Once you have that URL, run
   `supabase secrets set FRONTEND_ORIGIN="https://yourname.github.io"`
   again with the real value, so the functions' CORS check accepts requests
   from your live site.

Routing uses HashRouter (URLs look like .../#/teacher) specifically
because GitHub Pages can't rewrite arbitrary paths back to index.html the
way a real server can - this avoids needing a 404-redirect workaround, and
"deep" links and page refreshes just work.

## Redeploying after code changes

Frontend changes deploy automatically on every push to main (via the
GitHub Actions workflow). Edge Function changes need a manual redeploy from
your terminal:

```bash
supabase functions deploy auth      # if you changed supabase/functions/auth
supabase functions deploy teacher   # if you changed supabase/functions/teacher
supabase functions deploy student   # if you changed supabase/functions/student
supabase functions deploy wall      # if you changed supabase/functions/wall
```

## Later: mobile app

The Edge Functions are a plain REST API, so a future mobile app can reuse
them entirely unchanged. For a fully open-source, no-card mobile build,
React Native + Expo (open source, MIT-licensed, free Expo Go / EAS free
tier for builds) is the natural next step - it shares the same component
logic style as this React frontend, so porting screens over is
straightforward.

## Notes / defaults baked in

- A paper mixes any of four question types (MCQ, true/false, fill-in-the-blank,
  match-the-following), each with its own marks (default 1, teacher-adjustable);
  the paper's total is whatever those add up to.
- Grading for all MCQ-family types is a direct server-side comparison against
  the stored answer key - instant and free. Gemini is only used to generate
  questions, and (for short-answer papers) to OCR + grade a photo.
- A paper is visible on a student's landing page for 40 minutes after the
  teacher uploads it, then it moves into the collapsed dashboard archive for
  both sides; one attempt per student per paper regardless.
- Deleting a paper asks for confirmation once and cannot be undone.
- Times shown are the browser's local time zone.
- **Handling many students submitting at once:** the database pool is sized
  for a full class (~30-60 students) submitting within the same few seconds,
  the attempts table has a UNIQUE(mcq_set_id, student_id) constraint as
  the real source of truth for "one attempt only," and a race between two
  near-simultaneous duplicate submissions (e.g. a double-tap) now returns a
  clean "already attempted" message instead of a generic server error.
  idx_attempts_mcq_set speeds up the live-scoreboard query specifically
  during that same submission burst.
- **Document upload** (PDF/DOCX) is extracted to plain text entirely in the
  browser before it's ever sent anywhere - the backend only ever receives
  and stores plain text, never a binary file.
- **Short-answer photos** are sent straight to Gemini for grading and never
  stored - only the resulting mark and one-line feedback are kept.
- Supabase's Row Level Security (RLS) shows tables as "unrestricted" in the
  dashboard - this is fine here, since every request goes through an Edge
  Function using the service-role key, not directly through Supabase's
  public REST API from the browser.
